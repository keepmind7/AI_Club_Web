# Club Manager 개발 오케스트레이터

## 실행 모드: 혼합

| 단계 | 실행 모드 | 이유 |
| --- | --- | --- |
| 1. 구현 | 지속형 에이전트 (`backend`, `frontend`) 병렬 | QA 결과로 수정을 요청할 때 대화 맥락을 유지해야 한다 |
| 2. 검증 | 서브에이전트 위임 (`club-qa`, 단발) | 독립된 시각으로 한 번 검사하고 보고만 하면 된다 |
| 3. 수정 | 지속형 에이전트에 `SendMessage` | 1단계의 맥락을 그대로 이어 간다 |

## 기준 문서

- 요구사항: `동아리 통합 관리 시스템 개발 계획서.md`, `동작 흐름.md` (프로젝트 루트)
- API 계약: `references/api-contract.md` — 백엔드와 프론트엔드가 함께 따르는 유일한 기준. 이 계약 덕분에 두 에이전트가 동시에 일할 수 있다.

## 에이전트 구성

| 이름 | `subagent_type` | 맡는 범위 | 산출물 |
| --- | --- | --- | --- |
| `backend` | `club-backend-dev` | `backend/`, `docker-compose.yml`, `.env.example`, `.gitignore`, `README.md` | `_workspace/01_backend_report.md` |
| `frontend` | `club-frontend-dev` | `frontend/` (Dockerfile, Caddyfile 포함) | `_workspace/01_frontend_report.md` |
| (단발) | `club-qa` | 읽기·실행만 | 반환 메시지 → 메인이 `_workspace/02_qa_report.md`로 저장 |

## 작업 절차

### 0단계: 기존 작업 확인

- `backend/`, `frontend/`, `_workspace/`가 모두 없으면 **처음 실행**: 1단계부터.
- 코드가 있고 사용자가 일부 기능·버그만 요청하면 **부분 실행**: 해당 영역 에이전트만 띄우고, 요청 내용과 관련 파일을 프롬프트에 적는다. 그다음 2단계 검증.
- API 계약을 바꿔야 하는 요청이면 메인이 먼저 `references/api-contract.md`를 고친 뒤 양쪽 에이전트에 알린다.
- 이전 `_workspace/`가 있고 새로 처음부터 만드는 요청이면 `_workspace_{YYYYMMDD_HHMM}/`로 옮긴 뒤 시작한다.

### 1단계: 구현 (지속형 에이전트 병렬)

한 메시지에서 두 에이전트를 동시에 띄운다.

```
Agent(name: "backend",  subagent_type: "club-backend-dev",  prompt: <아래 공통 프롬프트 + "백엔드 범위를 구현하라">)
Agent(name: "frontend", subagent_type: "club-frontend-dev", prompt: <아래 공통 프롬프트 + "프론트엔드 범위를 구현하라">)
```

공통 프롬프트에 넣을 것:
- 기준 문서 세 개의 경로
- 맡은 범위 (위 표)
- 이번 실행의 요청 내용 (처음 실행이면 "첫 출시 범위 전체")
- 완료 시 `_workspace/01_{agent}_report.md`에 남길 것: 만든 파일 목록, 실행·테스트 명령과 결과, 계약과 다르게 구현한 부분(있으면), 남은 문제

두 에이전트의 완료 알림을 기다린다. 메인은 그동안 같은 코드를 직접 작성하지 않는다.

### 2단계: 검증 (서브에이전트)

```
Agent(subagent_type: "club-qa", prompt: <기준 문서 경로 + 두 보고서 경로 + "전체 검증하라">)
```

반환된 보고서를 `_workspace/02_qa_report.md`(재검증이면 `04_qa_report.md`)로 저장한다.

### 3단계: 수정 (최대 2회 반복)

- QA 보고서의 `필수 수정` 항목을 영역별로 나눠 `SendMessage(to: "backend" | "frontend")`로 보낸다. 항목마다 파일 위치와 근거를 그대로 붙인다.
- 수정 완료 후 2단계를 다시 실행한다.
- 2회 반복 후에도 남은 필수 수정 항목은 최종 보고에 그대로 적는다.

### 4단계: 마무리

사용자에게 보고한다: 만든 기능, 실행 방법, 테스트 결과(실제 출력 기준), 검증하지 못한 것, 남은 문제. `_workspace/`는 남긴다.

## 오류 처리

- 에이전트가 실패하면 한 번 다시 시도한다. 다시 실패하면 같은 `subagent_type`을 새 이름으로 띄우고, 부분 산출물 경로를 프롬프트에 넣어 이어서 하게 한다.
- 지속형 에이전트가 응답하지 않으면 `SendMessage`로 상태를 묻고 다시 지시한다.
- 사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다. 실제 진행 상황을 파일에서 확인해 `_workspace/`에 기록하고 사용자에게 보고한다.
- 두 에이전트가 계약을 서로 다르게 해석하면 메인이 계약 문서를 기준으로 판정하고, 계약이 모호했다면 계약을 고친 뒤 양쪽에 알린다. 에이전트의 판단을 추측해 채우지 않는다.
- Docker가 없는 환경이면 Docker 관련 파일은 작성만 하고 "실행 검증 안 함"으로 보고한다.
- `Agent type '...' not found`가 나오면 (에이전트 파일을 이번 세션에 만들어 아직 로드되지 않은 경우) `subagent_type: "general-purpose"`와 정의 파일의 `model`로 띄우고, 프롬프트 첫 줄에 "`.claude/agents/{name}.md`를 읽고 그 역할로 일하라"를 넣는다.

## 테스트 시나리오

### 정상 흐름
1. 사용자가 "동아리 앱 만들어줘"라고 요청한다.
2. 0단계에서 처음 실행으로 판단하고 `backend`, `frontend`를 동시에 띄운다.
3. 두 보고서가 생기면 `club-qa`가 백엔드 테스트, 프론트 타입 검사·빌드, 계약 대조를 실행한다.
4. 필수 수정 항목이 있으면 해당 에이전트에 보내고 재검증한다.
5. 필수 수정 항목이 0이 되면 실행 방법과 테스트 결과를 보고한다.

### 오류 흐름
1. QA가 "`/api/me/payments`의 `dues` 정렬이 계약과 반대"라고 보고한다.
2. 메인이 해당 항목을 `backend`에 `SendMessage`로 보낸다.
3. `backend`가 응답하지 않으면 상태를 묻고, 그래도 실패하면 `club-backend-dev`를 `backend-2`라는 이름으로 새로 띄워 보고서와 QA 항목을 넘긴다.
4. 재검증 후에도 남으면 최종 보고에 "미해결"로 적는다.
